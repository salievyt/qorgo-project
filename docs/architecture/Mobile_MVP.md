# QORGO: минимальный MVP и MVVM

Рабочий сценарий: регистрация → доверенный контакт с email его аккаунта → полное движение SOS-слайдера → входящий сигнал у близкого → «Помогаю» → подтверждение у отправителя → завершение тревоги.

## Границы слоёв Flutter

- `core/`: HTTPS-клиент, конфигурация окружения, базовый ViewModel с защитой после dispose, общий SOS-слайдер.
- `domain/`: сущности, интерфейсы репозиториев и устройства, сценарии с проверкой контактов и SOS. Нет импортов Flutter, HTTP или хранилища.
- `data/`: реализация репозитория, преобразование JSON в сущности, Keychain/защищённое хранилище, геолокация, карты, SMS и системный звонок.
- `feature/auth/`: модель входа и экран регистрации/авторизации.
- `feature/safety/`: SafetyViewModel с командами контактов, SOS и подтверждения, экран безопасности и формы.
- `feature/app/`: AppViewModel координирует сессию, AppView выбирает экран по состоянию сессии.
- `feature/subscriptions/`: ранее созданный экран сохранён, но в минимальном MVP не отображается.

`main.dart` — точка сборки зависимостей. View не обращается к HTTP, JSON или Keychain. Репозиторий внедряется через интерфейс domain. Состояние обновляется через ViewModel; обновление из сети опрашивается раз в 5 секунд и после возврата в приложение.

## Публичный сервер

По умолчанию используется `https://api.qorgo.services/api`, Django на существующем Vercel-проекте с постоянной PostgreSQL-базой. Для локальной разработки:

```sh
flutter run --dart-define=QORGO_API_URL=http://127.0.0.1:8000/api
```

Основные endpoints: register/login/logout, profile, contacts, alerts и inbox.

- `GET /api/inbox/`: входящие SOS для email авторизованного аккаунта; до 100 последних сигналов.
- `POST /api/inbox/{delivery_id}/acknowledge/`: идемпотентное подтверждение получателем.
- Получатель видит координаты отправителя, если они доступны; может открыть карту.
- Отправитель видит «доступен в приложении» и затем «получатель подтвердил». Сохранение SOS на сервере не приравнивается к прочтению.
- Контакты и получатели фиксируются на момент SOS; повтор запроса с тем же UUID не создаёт дубликат.
- Email контакта должен совпадать с email аккаунта близкого. Участники используют собственные пароли и токены; получатель не может завершить чужую тревогу.
- При сбое внешней отправки worker не перезаписывает подтверждение, которое уже сделал человек в приложении.

## Проверка на двух устройствах

1. Создать аккаунт близкого и аккаунт отправителя (разные email).
2. Отправитель добавляет близкого с email его аккаунта и телефоном.
3. На устройстве близкого открыть QORGO. На устройстве отправителя протянуть SOS-слайдер полностью вправо.
4. В течение следующего обновления у близкого появляется SOS. Нажать «Помогаю — подтвердить SOS».
5. У отправителя статус меняется на подтверждение; он завершает тревогу.

Входящий SOS появляется только когда приложение открыто и есть сеть. Push при закрытом приложении, подтверждение владения email, голосовой звонок внутри QORGO и диспетчерская служба не включены. Кнопка звонка открывает системный телефон. SMS требует настроенного провайдера или ручной отправки через системное приложение.

Таймеры сохранены в API для совместимости, но скрыты из MVP: на Vercel не работает постоянный worker, поэтому обещать срабатывание таймера независимо от приложения нельзя. Для возврата этой функции нужен отдельный worker/планировщик.

## Автоматические проверки

Flutter: `flutter analyze`, `flutter test`.
Django: `.venv/bin/python -m pytest`.
Проверка публичного API и настоящего iOS-приложения:

```sh
flutter test integration_test/in_app_sos_test.dart -d <iOS-device-id>
```

Тест создаёт два технических аккаунта с email на `example.invalid`, посылает SOS с тестовыми координатами через настоящий слайдер, проверяет входящий сигнал, подтверждение и завершение. Геолокация в этом тесте внедрена: системный запрос разрешения не автоматизируется. Тестовые аккаунты остаются в базе, токены отзываются; сторонние SMS/email не отправляются при зарегистрированном получателе.
